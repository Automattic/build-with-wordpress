# Generated Outputs

The `plugins/` tree is generated by `scripts/build-plugins.mjs` from the canonical `skills/` directory, generator templates, and the built telemetry MCP artifact. Generated files are part of the repository contract because downstream users copy or install them directly into their preferred coding-agent environment.

Source evidence: `README.md`, `scripts/build-plugins.mjs`, `scripts/build-telemetry-mcp.mjs`, `scripts/verify-plugins.mjs`, `scripts/export-cursor-plugin.mjs`, `package.json`, and `plugins/**`.

## Build contract

Run the generator from a clean checkout:

```bash
pnpm install
pnpm build
pnpm verify
```

`pnpm build` has two stages:

1. `scripts/build-telemetry-mcp.mjs` bundles `scripts/wordpress-telemetry-mcp.mjs` into `dist/wordpress-telemetry-mcp.mjs`.
2. `scripts/build-plugins.mjs` reads the shared skill names, removes and recreates generated output roots, copies or adapts skills, embeds telemetry bootstraps, and writes each surface's native files.

`pnpm verify` is the review gate. It checks that generated packages contain the expected files, skill copies, MCP configurations, telemetry server entries, manifests, and surface-specific artifacts.

## MCP and telemetry contract

Most MCP-capable outputs expose two server entries:

```json
{
  "wordpress-studio": {
    "command": "studio",
    "args": ["mcp"]
  },
  "wordpress-telemetry": {
    "command": "node",
    "args": ["<generated telemetry bootstrap>"]
  }
}
```

The exact object shape changes by surface. For example, VS Code-style outputs use a `servers` object, standard MCP JSON outputs use `mcpServers`, OpenCode uses its own `mcp` structure, and Zed uses `context_servers`. The meaning is the same: `wordpress-studio` connects to the existing Studio MCP server, while `wordpress-telemetry` runs a generated Node bootstrap that decompresses and imports the shared telemetry MCP bundle.

`createTelemetryBootstrapArgs()` in `scripts/build-plugins.mjs` compresses `dist/wordpress-telemetry-mcp.mjs` with Brotli, serializes it as base64, and creates a Node `--eval` payload. That avoids copying a large bundled server into every generated output while keeping each package self-contained enough to launch the telemetry MCP server.

## Generated package responsibilities

Every generated package should make the target agent WordPress-aware by providing some combination of:

- shared skills for task routing and implementation guidance;
- setup instructions for installing or copying the package into the target agent;
- MCP configuration for WordPress Studio and telemetry where the target supports MCP;
- surface-native manifests or metadata;
- rules or instructions that tell the agent to start with `wordpress-creator` and select the smallest correct WordPress abstraction; and
- verification guidance that uses Studio MCP, screenshots, block validation, WP-CLI, project tests, and generated-output checks.

## Failure modes and maintenance rules

| Failure mode | Likely cause | Correct fix |
| --- | --- | --- |
| A generated package is missing a skill | `skills/**` changed but `pnpm build` was not run, or the target uses a custom skill destination that was not updated. | Run `pnpm build`, inspect the diff, and update the target template or verification rule if the layout changed intentionally. |
| `wordpress-telemetry` entry is missing | The target has `includeTelemetry: false`, does not support MCP, or the template omitted telemetry wiring. | Confirm the surface's official integration shape, then update `scripts/build-plugins.mjs` and `scripts/verify-plugins.mjs` together. |
| `wordpress-studio` entry points to the wrong command | A surface-specific MCP serializer diverged from the shared Studio MCP contract. | Update the relevant helper or template to launch `studio mcp`. |
| `pnpm verify` fails after generator edits | The generated layout and verification expectations are out of sync. | Update source templates and verification checks in the same change, regenerate, and re-run verification. |
| Cursor export misses changes | `plugins/cursor/` was not regenerated or `pnpm export:cursor` was not run. | Run `pnpm build`, `pnpm verify`, and `pnpm export:cursor` or its dry-run form. |

## Cursor standalone publishing

Cursor requires a separate plugin repository. `scripts/export-cursor-plugin.mjs` uses `git subtree split --prefix=plugins/cursor` and pushes the generated subtree to `Automattic/wordpress-cursor-plugin` on `sync/from-build-with-wordpress`. The source of truth remains this repository: update `skills/` and the Cursor generator here, run `pnpm build` and `pnpm verify`, then export.

Use a dry run before pushing when validating publishing mechanics:

```bash
pnpm export:cursor -- --dry-run
```
